# Agent 编排能力基座 · 设计文档

- 日期：2026-06-23
- 状态：设计 + UI 设计稿已定（`agentre.pen` 14 帧），待转实现计划
- 范围：`agentre/`（Wails 桌面端，Go 后端 + React 前端）

## 1. 背景与目标

仓库里已有一批多 agent 编排原语：`subagent`（同步委派子 agent）、`group`（群聊 + 任务卡 + 主持人 + 调度器）、`workflow`（SOP 文本注入）、`org`（组织架构读写）、通用 `tool_approval`、daemon 反向隧道。但它们要么是同步单发，要么绑死在"群聊"这个具体形态上。

**目标：提供一套"Agent 编排能力基座"**，让多个 agent 在**用户自然语言指导下自行编排协作**——而不是由代码写死某条固定流程。

**北极星（仅作表达力测试，不写死）**：
> 用户发任务给 leader → leader 先想"怎么做 + 验证目标/测试" → 拆分并行派给多个 dev → dev 完成交代码评审 → 全部通过后交测试 agent 做真实 e2e → 不过则打回开发，直到通过 → 通知 leader 决定收口。

这条流程**一行都不写死**；基座的职责是让 agent 们能自己拼出它**以及任意别的流程**。

## 2. 已锁定的设计取向（关键决策）

1. **涌现式（emergent）**：v1 只做"AI 自己编排"，**不做**确定性图引擎 / 可插拔双引擎（以后再说）。
2. **唯一原语 = 任务（Task）**：一个 agent + 一段 brief + 一条持久会话。审核、合并、返工都是"普通任务"，不是内置阶段。
3. **一切结果回到调用者；Leader 是 hub**：没有横向转交（**无 handoff**）。子任务完成 → 回报派发者 → 由它决定后续；顶层回报 Leader，Leader 决定全局后续。
4. **无内置门 / 阶段 / barrier**：不强制"执行→审核"两段式、不内置"集成门"。要不要审核/合并、何时收口，全由编排 AI 临场决定。
5. **无上限**：不限制续做轮数、时长、成本（"续做"= 派发者再 `send`，不是一种被计数的"返工态"）。
6. **尽量不介入，但保留可见的用户介入口子**：默认全自治；用户可随时主动介入（见 §3.2）。不做隐藏兜底。
7. **危险工具审批 = 各 agent 后端自身配置**：编排层不新增审批层。
8. **上下文流 / worktree 合并冲突 = AI 编排决定**：runtime 只提供原语。
9. **不做崩溃自动恢复**：任务持久化；重启后用户进 Leader 会话，Leader 自检续跑。

## 3. 能力基座

### 3.1 Agent 面向的编排原语（MCP 工具）

任何 agent 启用即可调用 → 编排天然递归成树。

| 工具 | 语义 | 轮次性质 | 复用 |
| --- | --- | --- | --- |
| `dispatch(agent, brief, {isolate?})` | 派一个任务给某 agent，新起一条子会话异步跑，**结果回报派发者** | **一次性调用-返回**；可对同一 agent 反复多次调用（这就是"子agent"） | `subagent.agent_call`，改为异步并行 |
| `ask(agent, question)` | 向另一个 agent 提问，**答案回报提问者**；目标忙则排队、空了再答；提问方挂起等回复 | **多轮问答** | group 调度器 `pending/inflight` + 阻塞式工具调用 |
| `send(taskId, message)` | 往**自己派发的某任务**会话里发后续/返工反馈（**同会话续做**），更新后的结果再回报自己 | 续接同一会话 | `chat_svc` 续轮 |
| `finish(summary)` | 收口当前任务/Run，向上回报 | — | — |

> "审核"= dispatch 给评审 agent；"合并"= dispatch 给某 agent 跑 git；"返工"= send 进原任务会话。都不是独立工具。

### 3.2 Runtime 机制（护栏 + 接力，非 agent 工具）

- **完成回报续轮**：任务完成 → runtime 把结果作为消息**续轮**进派发者会话，触发其下一轮决策。复用现有"后台任务自主续轮"（`AutonomousTurnSource`）。
- **任务完成判定（杜绝卡 `运行中`）**：一个任务在其 agent **本轮结束、且无未决事项**（没有"已派发未回报"的子任务、没有阻塞的 ask / 审批）时即 `done`，以该轮**最后产出**作为回报交回派发者。`finish(summary)` 是**显式且首选**的收口（给出干净的结构化报告），但**安静的轮结束同样收口**——不依赖 agent 记得调 `finish`，从根上杜绝"轮已停、状态没翻、卡 `运行中`"（本仓库已知坑 [[project_stuck_running_lost_status_write]]）。**完成态从会话真实空闲推导**（不只看一个状态标志位），状态写失败也能被对账纠正。**premature-done 无害**：派发者必读报告，觉得没做完就再 `send` 续做（§5），由"一切回到调用者"兜住。`finish` 落在 Leader（根任务）上 = 整个 Run 收口。**根任务例外**：Leader 在两次子回报之间空闲 ≠ Run 完成（它还在等下一个回报）——**Run 收口只认 Leader 显式 `finish`**，根任务不走"安静轮结束"的自动收口；否则"杜绝卡运行中"会反向变成"Run 提前完成"。子任务的 premature-done 由派发者再 `send` 兜住，但根之上没有更高派发者，故根必须显式收口（用户也可随时"对 Leader 说"重新唤醒）。
- **并行执行 + worktree 隔离**：`isolate` 的任务各跑独立 git worktree（注意 worktree 内 `GOWORK=off`、`wailsjs/dist` 是生成物需先 generate 等已知坑）；不 isolate 则共享 workdir。
- **并发调度器**：同时在跑的任务有上限 N + 排队（参考 `min(16, 核数-2)`）。**这不是工作量上限**——所有任务都会跑，只是不同时跑爆机器。
- **用户介入口子**（可见、用户主动开）：
  - **暂停 / 恢复**：暂停整个 Run 或单个 agent（当前轮跑完后挂起）。
  - **硬停止**：停止 Run → **级联取消子任务 + 清理 worktree**。
  - **对任意对话发言**：点开任意任务/Leader/ask 线程直接发消息 → 进入该会话触发其下一轮（对 Leader 说=改全局；对 worker 说=局部纠偏；也可替它答问题、接管）。
  - **阻塞式确认（按需，且按分支阻塞）**：两个来源——① **危险 / 有副作用的工具操作**（改 schema/DB、`rm`、`push`、网络）走**各 agent 后端自身权限**（§2.7），命中即该任务进 `awaiting-user·审批`、**该分支挂起**直到批准 / 拒绝（**此安全网取决于该后端权限配置**：若某后端被设为自动放行，编排层不再加门，危险操作会无确认直接执行——故创建 Run 时应让用户看见各 agent 的"危险操作自动放行 / 需审批"姿态，见 §8）；② **agent 自己拿不准的判断**：它结束本轮、以 `blocked` **回报派发者（通常是 Leader）**，由 Leader 自主决定（多数不必惊动用户）；仅当 Leader 主动上抛才变成 `awaiting-user·回复`。**阻塞按分支、不是整 Run**——兄弟任务照跑，挂起分支等你或 Leader 解；因此不会出现"别的都跑完了你才来决定"的尴尬。
  - **FYI / 假设（非阻塞，不是收件箱）**：agent 可在自己的流里冒一条"我假设了 X（不符请纠正）"。它**不排队、不等回答**，只是活动流里的一条提示；要纠正就用上面的"对任意对话发言"。**不做"可回答又可忽略"的软请求队列**——要么真需要答复就阻塞，要么只是 FYI，二选一，避免消费侧困惑。
- **工具审批**：危险文件/bash/网络沿用**每个 agent 后端自身权限配置**（即上面的阻塞来源①），编排层不新增审批层；编排自身的写工具仍走现有 `tool_approval`。

### 3.3 AI 编排如何发生（编排智能从哪来）

"编排"**不是某段编排引擎代码**，而是**编排者 agent 用上面的工具、被恰当指引后自己推理出来的**。编排"智能"来自三处叠加：

1. **用户的自然语言目标与持续指导（主导）**——"做什么、怎么协作"由用户说；如何编排由用户指导、agent 执行。
2. **runtime 每轮自动注入的"编排指引"system-prompt 块**（对启用了编排工具的 agent）——讲清：你有 `dispatch/ask/send/finish`；模型是"**一切结果都会回到你、由你决定下一步**"；可用团队来自 `agent_list`；常见模式（并行派发、评审/测试/合并也是派任务、返工用 `send`、收口用 `finish`）；**无次数上限，所以要自己判断何时收口或换策略**；用户可能随时插话、需要时可发软请求但别依赖。复用现有 group/subagent 的注入套路（`TurnMCPProvider` + system-prompt 后缀）。
3. **编排者自身 persona（可选）**——用户给 Leader 配的角色提示（如"软件交付协调者"的拆分/验收规范）。

**涌现控制环（编排者视角，全是普通 LLM 轮 + 工具调用，无额外引擎）：**

1. 接目标 → **思考轮**：理解、拆分、定"验证目标/测试"（纯对话，不调工具）。
2. **派发轮**：并行 `dispatch` 子任务（是否 `isolate` 自定）；需要信息就 `ask` 同伴。
3. 子任务完成 → runtime **续轮**把结果送回编排者会话（它"醒来"）。
4. **决策轮**：据回报决定——再 `dispatch`（评审/测试/合并）/ `send` 返工 / `ask` 补信息 / 或 `finish`。
5. 循环 3–4，直到 `finish`。

> runtime 的全部职责是"**在正确时刻把结果续轮回编排者**"，让这个 LLM 驱动的环转起来；它**不替 agent 做任何编排决策**。

**用户的角色**：起 Run 时给目标 + 指定 Leader（+ 可选限定可调度的 agent 子集）；过程中随时插话（§3.2 口子）。

**编排质量的杠杆（是影响因素，不是机制）**：编排指引 prompt 的质量、Leader 所用模型档次、团队中各 agent 的能力描述写得是否清楚（写清 `agent_list` 才派得准）。

### 3.4 明确不内置

无 handoff（横传）· 无集成门/barrier · 无固定阶段 · 无确定性图引擎 · 无重试/成本/时长上限 · 无自动崩溃恢复。

## 4. 边界与失控处理

- **上下文 / 产物如何流**：删掉 handoff 后，context 经三条路传递，**由 AI 编排决定**：① Leader 在 dispatch 时把产物引用写进 brief；② 共享工作区/产物让被派 agent 自己读；③ 结果回报 Leader、Leader 在下一次 brief 里带上。runtime 提供工作区 + 产物引用能力，不规定流法。
  - **`isolate` 的跨 worktree 共享有边界**：隔离任务各在独立 git worktree，**彼此看不到对方工作树的文件**——所以②的"共享工作区自己读"只对**不 isolate、共享 workdir** 的任务成立；isolated 任务之间只能走①③（回报里的**产物引用** + Leader 再派时带上）。runtime 提供：产物引用登记（即 UI 的 **Blackboard / 产出物**）+ worktree 句柄，但**不自动跨树同步文件**。要把多个 worktree 的产出落到一处 = Leader **再派一个"合并"任务**（见下条），冲突再派"解冲突"任务。
- **并行 worktree 合并 + 冲突**：物理合并仍要发生，但**不内置"集成门"**——由 Leader **再派一个"合并"任务**完成；合并冲突则再派"解冲突"任务。全是普通任务。
- **失控（无上限的代价）**：不加硬上限；唯一兜底 = **用户可见 + 可停**。因此 UI 必须把**任务树规模（节点 / 深度 / 总数）、累计 token / 时长、各分支状态**显著顶出来，并提供硬停止。**软阈值预警（非硬上限）**：当树规模 / 累计 token / 时长越过默认或用户设定的软线时，runHeader 给一条**非阻塞预警**，把"可见"从被动一瞥变主动提示——但**绝不自动暂停或封顶**（守 §2.5）。（没有"返工次数"这种指标——返工不是实体，见 §5。）
- **技术错误（运行中崩溃 ≠ 重启）**：某任务运行时崩溃（CLI 进程退出 / 不可恢复异常）→ runtime 标 `error`，并**当作一种回报上抛给派发者**（与 `blocked` 同一条续轮路），让 Leader 即时决定（再 `dispatch` 重试 / 换 agent / 放弃该分支），**不必等整体重启**。该分支停在 `error` 上、不静默吞掉；兄弟分支照跑。（与下条"崩溃/重启"区分：那条说的是整个 app 进程挂掉后的恢复。）
- **崩溃 / 重启**：不自动恢复。任务（= 会话）已持久化；进行中的那一轮丢失。重启后用户进 Leader 会话，Leader 用 `task_status` 自检哪些完成/中断，自行 `send`/`dispatch` 续跑。
- **ask 死锁**：A→B→C→A 的等待环——把 dispatch 祖先链（`resolveChain`）扩成 **dispatch+ask 合并等待图**做环检测；命中后**在 UI 上高亮该环（涉及的 ask 边 / 节点）并交给 Leader / 用户决定**，而非静默强行让一方作答（守 §2.6 "不做隐藏兜底"）。

## 5. 数据模型

新领域包 `orch_entity` / `orch_repo` / `orch_svc`（与 group/chat 平级）。迁移**追加到 `migrationList()` 末尾**，DDL 用原生 SQL。

- **`OrchestrationRun`**：`ID`、`Goal`、`LeaderAgentID`、`Status`（pending/running/paused/done/stopped）、`RootTaskID`、时间戳。（Run 不单设 `error`；根任务技术崩溃时 Run 仍 `running`，由**根任务自身 `error`** 体现并在 UI 提示。）
- **`Task`**：`ID`、`RunID`、`AgentID`、**`SessionID`**（复用 `chat_entity.Session`，每任务一条持久会话）、`ParentTaskID`（成树）、`Kind`（`dispatch`/`ask`）、**`Status`=客观生命周期**（`pending`/`running`/`awaiting-children`/`awaiting-user`/`done`/`canceled`/`paused`；技术崩溃才有罕见 `error`）、`Brief`、`Result`、`CallSeq`（子agent 第几次调用）、`Refs`（被引用的产物/任务）。
- **状态 vs 结果（关键区分，勿混）**：`Status` 是 runtime 客观可知的生命周期，驱动 UI 颜色 / 计数；而"评审通过 / 驳回 / 合并完成"等是 **agent 自报的语义结果**，落在 `Result.summary`（自由文本），**不是固定状态枚举**——并非每个任务都有"驳回 / 返工"（如"跑 git merge"任务只有 `done` + summary）。UI 用客观 `Status` 做状态胶囊，把语义结果作为结果文本展示。
- **没有"返工 / 失败(语义)"这种实体**：子任务只是 `run → done`、把**报告**交回派发者；"成功 / 失败 / 要不要返工 / 要不要再派"全是**派发者读报告后的判断与决定**（再 `dispatch` / `send` / `finish`），不是子任务自身的状态。所谓"返工"不过是派发者对**同一任务**再 `send` 一条——**同一节点再次 `运行中`，不新增节点 / 边**（新节点 / 边只来自 `dispatch`）；**不计数、不设"返工态"**；迭代历史在该任务 transcript 里看，不做 `⟲×N` 指标。
- **结果契约**：子任务交回派发者的是一份**报告**——自由文本 `summary` + 产物引用；唯一的结构化信号是 `blocked`（需输入才能继续 → 按分支阻塞 §3.2）。**不带 done/failed 的"成败"枚举**——跑完即 `done`（完成本轮、交回报告），成败由派发者读 summary 自行判断；技术崩溃才是 runtime 的 `error`。
- **等待状态的 UI 归并**：`awaiting-children`（等子任务）与 `ask` 等待（等同伴答复）在 UI 上并为一个『**等待中**（其他 agent）』胶囊（非琥珀、表示推进中、无需你）；只有 `awaiting-user`（审批 / 回复）用琥珀『**等待你**』。用户只需分辨『等我』vs『等系统』，无需关心是等子任务还是等同伴。（机制上一个任务可**同时**等子任务与等 ask 答复：`ask` 挂起的是发起那一轮的推理，但其先前 `dispatch` 的子任务回报仍会照常续轮唤醒它。）
- 子会话不渗进普通会话列表（复用 subagent 的会话隔离）。

## 6. 复用映射（净新增很少）

| 能力 | 复用现有 |
| --- | --- |
| `dispatch` | `subagent_svc.agent_call`（改异步并行 + 完成回报，不再同步阻塞） |
| `ask` 排队 | group 调度器 `pending/inflight` 投递 |
| 完成回报续轮 | `AutonomousTurnSource`（后台任务自主续轮） |
| 任务执行 | `chat_svc` turn 机制 + `chat_entity.Session` |
| 并行隔离 | 现有 worktree 基建 |
| 编排工具注册 / 门控 | `agenttool` 注册表 + `TurnMCPProvider` + `ToolEnabled` |
| 编排写工具审批 | 通用 `tool_approval` |
| Leader 可调度花名册 | `org` / `agent_list` |
| 远端执行 | daemon 反向隧道（org/subagent/group/workflow 已通） |

**核心唯一新机制** = 把 subagent 的"同步阻塞单发"改造成"**异步并行多发 + 完成回报续轮**"；其余皆装配现有件。

## 7. 编排范围与能力门控

- **谁能当 Leader / 谁能子派**：任何**启用了编排工具**且**后端声明 `CapMCPTools`** 的 agent（Claude Code / Codex 声明；内置 piagent 暂无 MCP 支持）。Leader 与子派无特殊身份，只是树上的位置。
- **可调度对象**：Leader 经 `agent_list` 看到 org 内可用 agent 及其能力/角色，据此拆活。
- **跨后端**：一个 Run 可混用不同后端的 agent，但只有 `CapMCPTools` 后端能调用编排工具。

## 8. UI / UX

**创建一个编排 Run（取代"新建群聊"入口）+ 流程复用**：

- 左栏「新建 → 编排 Run」三项：① 选 **Leader agent**（取代群主持人）② 给**目标**（这次做什么）③ 选/写 **编排流程**（这次怎么协作）；（可选）限定**可调度团队**（团队选择处标注各 agent"危险操作自动放行 / 需审批"姿态，让用户起跑前知晓爆炸半径，机制见 §3.2）。启动 → 建 `OrchestrationRun`，根会话 = Leader 会话，**编排流程注入 Leader 的 system-prompt**。
- **不必每次手写流程**：**编排流程来自可复用的"编排流程库"**（重定位自现有 `workflow` 功能）——选一个保存好的流程即可；也可临时写一段，或留空走 Leader persona 的默认协作风格。
- **随时覆盖**：起 Run 时改写编排流程，或过程中插话临时调整（"这次跳过 e2e""加个安全审计"）。

**双视图 = runHeader 内分段控件切换的姊妹视图**（不并排塞同屏；两视图共用同一外壳与 Run 数据，由 runHeader 里的 `结构图 / 活动流` 分段控件切换；左 Rail 仅作 app 区段导航[编排 / 聊天 / 文件 / 组织]，**不**承担 per-Run 视图切换）：

- **结构图视图**（pencil 帧 `编排 Run — 结构图`）：三区 = 左 RunList（Run 列表 + 会话）｜ 中 **结构图画布** ｜ 右 **任务看板栏**。
  - **画布**：**agent 卡为节点，dispatch 边连到卡头**；卡内**任务行**（同一 agent 多任务 = 多行）；任务行下**嵌套 ↳ 子agent 行**（标 `一次性`）；运行中卡带底部**实时活动 tail**。Leader 居顶（皇冠标记），dispatch 向下分叉到各 worker。
    - **节点取 agent 还是 task（已定）**：对比过『任务为节点』(每 dispatch 一个节点、边精确) 与本『agent 节点 + 卡内任务行』后**选定 agent 节点**——取其简洁。代价：同一 agent 的多任务 / 混合态在卡级聚合（一条边、一个聚合状态），精确的任务粒度看**卡内行**与**右侧任务看板**。
  - **三类边**：**dispatch ↓** = 蓝实线（`$primary`，带箭头）、**完成回报 ↑** = 绿（`$status-running`，箭头指回 Leader）、**ask 平级** = 粉（`$agent-7`，挂 `ask·N轮` 标签）。画布右上角放**边图例**。注：`.pen` 无 stroke-dash 属性，"虚线"在设计稿中以颜色 + 细线近似，落地前端用真 dash。
  - **任务看板栏**：tab `任务看板 ｜ 产出物`；以任务为中心的清单——`#` / 负责 agent 头像 / 任务名 / 状态；**子agent 缩进**。底部常驻"点任务 / 节点 / 边 → 展开真实 transcript"。
- **活动流视图**（pencil 帧 `编排 Run — 活动流`）：同一外壳（同样的 RunList / runHeader / 右任务看板栏），中栏换成按时间排的活动 feed（dispatch / 回报 / `send` 续做 / ask / 用户插话 / 阻塞确认，**语义结果直接作为文本叙述**——正印证"结果是自由文本、不是状态枚举"；状态胶囊只用客观生命周期，不出现"开发中"这类与某流程强绑定的词）；顶部为阻塞确认条，底部为"对 Leader 说"输入条。

**顶部 runHeader = 速览 + 干预条 + 视图切换**（两视图共用）：标题 + `结构图 / 活动流` 分段控件 + `自主运行中` 状态 + token/时间 + **暂停 / 硬停止**；下一行 **客观状态计数（运行 / 等待你 / 完成）+ 树规模（节点 N · 子agent M · 深度 D）+ 累计 token / 时长**——`等待你` 琥珀高亮（唯一真正需要你的状态）；失控兜底靠树规模 + token/时长看得见（§4），**不设"返工次数"指标**。

**介入口子**（机制见 §3.2）：暂停 / 硬停止（runHeader）；**点任意节点 / 任务 / 边 → 展开该会话 transcript 并可发言**（"对 Leader 说"也常驻中栏底部）；**阻塞式确认**——危险操作 / agent 上抛的判断进 `等待你·审批/回复`，结构图里表现为该**节点变琥珀边 + 内联 `批准 / 拒绝`**、活动流里为**顶部阻塞条**（不可忽略、按分支阻塞）；**FYI / 假设**仅是节点 / 流里一条非阻塞提示，不排队不等答复。

**通知**：`等待你` 阻塞确认、Run 完成 → 桌面通知（复用 PushNotification）。

**创建入口已落地**：pencil 帧 `创建编排 Run 弹窗`（Leader / 项目 / 编排流程[流程库 or 临时写 or 留空] / 限定可调度 agent）。

**其他**：多 Run 并存（左栏 Run 列表，编排 Run 与普通会话并列）；大图**折叠 / 过滤 / 聚焦 + 小地图**，看板更扛规模（已落地帧 `编排 Run — 结构图 · 大图`：紧凑 chip 节点的密集树 + 折叠分支 `▶N` + 右下小地图[全树缩影 + 视口框 + 屏外节点提示] + 顶部图工具条 `缩放 / 适应 / 折叠 / 过滤 / 聚焦`）；**事后审计**——完成的 Run 回看整棵树 + 每条真实 transcript（复用聊天流 + block 级虚拟化）。

**Run 生命周期的三种视图态**（同一结构图随 Run 状态切换形态）：

- **空 / 起步态**：Run 刚建，画布只有 **Leader 一个节点**（`运行中` · "正在理解目标、拆分中…"），无 worker、无边；右看板只有 `#1 总目标`；速览 `节点 1 · 深度 0`；居中一句引导"Leader 规划完会自动派发子任务"。已落地帧 `编排 Run — 空·起步`。另有 `编排 Run — 无 Run 首次态`：编排区段一个 Run 都没有时——RunList 空态 + 画布居中 onboarding（`创建你的第一个编排 Run` CTA + 三步说明）。
- **进行中态**：即当前主帧（dispatch / 回报 / ask、阻塞、FYI 实时演进）。
- **完成 / 审计态**：Leader `finish` 后——节点全绿、画布顶部 **"✓ Run 完成"横幅**（用时 · 累计 token · 任务数 · 子agent 数）+ Leader 一张**交付小结**；runHeader 的 `自主运行中` → `已完成`，`暂停 / 硬停止` → `归档 / 导出`；进入**只读审计**：点任意节点 / 边 → 真实 transcript（复用聊天流 + block 级虚拟化）。已落地帧 `编排 Run — 完成·审计`。

**边缘 / 异常态（已落地帧）**——同一结构图外壳套不同情形：

- **ask 死锁高亮**（帧 `编排 Run — ask 死锁`）：检测到 `A→B→C→A` 等待环时——三方卡片红边、画布顶部红色横幅（"检测到 ask 等待环：王→李→测试→王 · 三方互等、无法推进 · 去裁决"）、底部红色 ask 环边 + `等待环 · 3 方` 芯片；不静默强答，交 Leader / 你裁决（§4）。
- **节点钻入 + 等待你介入**（帧 `编排 Run — 节点钻入`）：点某节点 → 该节点蓝色选中环 + 右栏从任务看板切成**该会话 transcript**（消息 / 工具调用 / 你的插话）+ 底部"对它说"输入；若该节点 `awaiting-user`，transcript 内联**阻塞审批块**（`批准 / 拒绝`）。印证 §8"点任意节点 / 任务 / 边 → 展开 transcript 并发言"。
- **暂停 / 技术错误**（帧 `编排 Run — 暂停·错误`）：整 Run `已暂停`（runHeader 状态灰、`暂停`→`继续`、计数归零）+ 某节点**技术崩溃 `error`**（红边 / `技术中断` / "运行时崩溃 exit 1"）；画布顶部横幅说明"恢复后 Leader 用 `task_status` 自检中断任务并续跑"（§4 崩溃 / 重启不自动恢复）。

**活动流（feed）侧的同态帧**：上述生命周期 / 边缘态在活动流视图有**同构姊妹帧**——区别在于中栏是按时间排的事件流、顶部状态条随态改写（阻塞确认 / 死锁警示 / 完成小结 / 暂停通知），feed 事件文案随态调整：`编排 Run — 活动流 · 空·起步`（仅"创建 Run / 规划中"两条事件、无阻塞条）、`… · ask 死锁`（顶部红色等待环条 + 三条 ask 事件 + 检测事件）、`… · 完成·审计`（顶部绿色完成小结 + finish 事件、`只读审计`）、`… · 暂停·错误`（顶部暂停条 + 崩溃事件）。活动流的『**进行中 + 等待你阻塞确认**』即主帧 `编排 Run — 活动流`（顶部琥珀阻塞条 + `批准 / 拒绝`）。**无 Run 首次态**（与视图无关）与**节点钻入**（右栏 transcript 交互两视图一致）不另出 feed 帧。

> **设计稿落地状态（`agentre.pen`，dark）**：核心三帧 `创建编排 Run 弹窗` ✓、`编排 Run — 活动流`（时间线视图）✓、`编排 Run — 结构图` ✓；结构图生命周期 / 边缘态六帧 `编排 Run — 空·起步` ✓、`编排 Run — 无 Run 首次态` ✓、`编排 Run — 完成·审计` ✓、`编排 Run — ask 死锁` ✓、`编排 Run — 节点钻入` ✓、`编排 Run — 暂停·错误` ✓；活动流同态四帧 `编排 Run — 活动流 · 空·起步` ✓、`… · ask 死锁` ✓、`… · 完成·审计` ✓、`… · 暂停·错误` ✓；大图缩放帧 `编排 Run — 结构图 · 大图` ✓。两视图共用外壳，经 runHeader 内 `结构图 / 活动流` 分段控件切换（Rail 仅 app 区段导航）。状态胶囊已改**客观生命周期**、确认改**按分支阻塞**（危险操作走 agent 后端权限 + 内联 `批准/拒绝`）、**取消"返工/失败"作为任务状态与"返工 N 次"指标**（子任务只 run→done 交回报告，成败与后续由派发者判断）、FYI 为内联非阻塞提示。待办：light 主题、产出物（Blackboard）tab 展开态。

## 11. 替代群聊（删 group，能力并入编排）

**结论：群聊可干净砍除，编排是其超集。** 群逻辑高度模块化、与普通单聊不纠缠（`defaultSessionScope` 过滤 `group_id=0`）；app 未发布、可 hard delete、无需兼容层。涉及面：后端 ~57 文件引用 group、前端 ~22 个 group-chat 组件、5 张表、若干 e2e；真正要小心的是 `chat_svc` 那 ~300 行接缝，其余多为文件级删除。

**概念映射（群 → 编排，近乎 1:1）：**

| 群聊 | 编排 |
| --- | --- |
| Group（会话容器） | `OrchestrationRun` |
| HostAgentID（主持人） | `LeaderAgentID` |
| GroupMember（固定 8 人 + 群昵称 + 各自 backing session） | 可调度团队（org/agent_list 动态、可选限定）；每任务一会话 |
| GroupTask（任务卡 create/complete/cancel） | `Task`（dispatch） |
| group_send（成员发言/@） | dispatch / ask / send |
| WorkflowID 绑定（SOP 注入 host） | **编排流程**（创建时选/写，注入 Leader）——见 §8 |
| scheduler（pending/inflight fan-out） | 编排 runtime 调度器 + 完成回报续轮 |
| group_create MCP 工具 | 不需要（Run 由用户建；agent 自发起编排 = 直接 dispatch） |

**删 / 改 / 留：**

- **删**：`group_entity` / `group_repo` / `group_svc`（用户面逻辑）/ `app/group.go` / 全部 group-chat 前端组件与 store / `group_create` 工具 / group 迁移表 / group e2e。
- **改（`chat_svc` 接缝 ~300 行）**：移除 group 的 `TurnMCPProvider`/`TurnExtrasProvider` 注册与实现；`defaultSessionScope` 改为按编排维度（RunID）隐藏子会话。
- **留 / 复用**：scheduler 的 pending/inflight 模式 → lift 进编排 runtime（非删）；**`workflow`/流程库 → 重定位为"编排流程库"**（`workflow_svc` 保留，去掉 group 计数、改 Run 计数）。

**会一并失去（已与用户确认取舍方向）**：

- "群聊天室"式单一共享对话流（多 agent + 用户同处一个气泡流）→ 改为任务树 + 逐会话介入。
- 群昵称、固定成员名单等群专属交互。

**实现顺序**：先建 orch 新域 + 复用 scheduler / 重定位流程库 → 再砍 group。**这两段应拆成两个独立实现计划**（plan-1 建 orch、plan-2 删 group），不要并成一个大计划——group 删除面广（见本节开头：后端 ~57 文件 + 5 表 + `chat_svc` ~300 行接缝 + 前端 ~22 组件 + e2e；按 `group` 子串粗筛后端 `.go` 命中可达 ~114，含注释/无关词，需逐一甄别），且建新域与删 group 互不阻塞、可分别验收。
